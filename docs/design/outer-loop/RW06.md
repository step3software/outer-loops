# RW06 — Timeline Keys

**Status:** Proposed milestone; owner requested its creation, not approval of the detailed mechanics.
**Repository:** `step3software/outer-loops`.
**Owner origin:** Conversation on 2026-11-06: introduce keys analogous to Path of Exile maps, giving the next run different attributes; subsequently requested a separate RW milestone.
**Sequence:** Follow-on to the initial Real World release; its numeric ID does not make RW05 a prerequisite.
**Implementation authorization:** None.

## Objective

Give players a deliberate way to enter a new timeline with a distinct, previewable set of rules and opportunities. A **Timeline Key** configures one whole timeline, rather than changing the rules of a single ordinary inner loop. Keys must change meaningful planning choices, not merely increase numerical difficulty.

## Player journey and scope

1. In Real World, the player can inspect available keys and their full effects, and can elect to start an ordinary timeline without a key.
2. Selecting one key previews its benefits, costs, affected gameplay systems, special win conditions (if any), compatibility limits and potential rewards before any commitment.
3. Starting a timeline commits a **versioned, immutable key configuration** to that timeline. The effective modifiers survive inner-loop restarts, save/reload, and export/import without silently rerolling.
4. The active timeline shows a concise key summary, with details available on demand; completion records an outcome and any earned key-specific reward exactly once.

**Initial implementation scope (proposed):**
- A small curated set of keys illustrating different tradeoffs, including at least two distinct rule domains (for example, economy versus progression or combat); examples are **not approved balance numbers**.
- A typed, data-defined modifier contract with stable IDs, explicit activation scope, bounded combinations and clear conflict/precedence rules; deterministic calculation shared by the runtime and predictor.
- Safe key selection, preflight validation, durable timeline commitment, reset handling, error presentation and an unmodified ordinary-timeline path.
- A single player-facing place for variant rules, coordinated with [RW04](roadmap.md), rather than rebuilding the old standalone Challenges interface.
- Outcome/reward integration with the existing Real World timeline lifecycle and archival summary, with no duplicate grants.

**Out of scope:** Full procedural affix generation and rarity tiers, key trading, complex crafting/rerolling, unlimited stacking, additional towns, parallel full-game simulation, rewriting legacy challenges as part of this feature, and monetary purchasing. These may be considered separately.

## Dependencies and gates

- **Hard:** [RW02](roadmap.md) must establish safe timeline creation, completion and outer-state persistence; [RF02](../../refactoring/RF02-persistence-safety.md) must provide the save/import/rollback safeguards needed before consuming or committing a key.
- **Hard contract:** Reconcile this feature with [RW04](roadmap.md)'s divergent-timeline rule system and the [Real World technical architecture](technical-architecture.md). Do not ship two competing rule evaluators or challenges menus; RW04 implementation itself is not assumed complete.
- **Engineering:** Shared gameplay rules, especially [RF03](../../refactoring/RF03-gameplay-rules-and-resources.md), must be deterministic without DOM dependence and equivalent in predictor/worker execution. Preserve all existing action identities and nine town indices.
- **Non-blocking:** RW05's multi-self management is not necessary for the initial key feature. [RW07](RW07.md) may later reference a committed key but does not change key rules.
- **Owner decisions still open:** How keys are earned, whether/when consumed, curated versus generated modifier pools, number and stacking limits, conflicts, reward economics, and any unique-key narrative effects. Do not implement assumed answers.

## Acceptance criteria

- **RW06-AC01:** A player can inspect a key's complete material modifiers before starting and can choose an unkeyed run; no prior or in-progress timeline changes from browsing.
- **RW06-AC02:** At least two curated keyed scenarios produce observable, distinct planning tradeoffs relative to the same unkeyed baseline; the modifier and conflict evaluation is deterministic.
- **RW06-AC03:** A successful new-timeline commit fixes key ID, definition version and effective modifier snapshot; restart, refresh, export/import and predictor read the same effective rules.
- **RW06-AC04:** Invalid, incompatible or interrupted key selection cannot consume an entitlement, mutate the previous timeline, or leave an unrecoverable half-committed run.
- **RW06-AC05:** Completing a keyed timeline records the correct key/outcome/rewards once; reload, revisit, re-evaluation and failed retries cannot duplicate them.
- **RW06-AC06:** Ordinary unkeyed play, existing timeline state, original actions, standard replay acceleration and any supported legacy save remain compatible.
- **RW06-AC07:** Key-modified outcomes and action eligibility agree between the actual game and predictor/worker in representative economy, time-gate and progression cases; performance remains bounded without running a second full game engine.
- **RW06-AC08:** A single compact interface explains active key effects and allows details without permanently cluttering the one-screen Real World/timeline view.

## Deliverables and verification

Prepare a key/modifier schema and UI flow; a small balanceable sample catalog; compatibility and conflict matrix; explicit reset/commit/reward contract; and reproducible tests for keyed and unkeyed timelines, malformed keys, save recovery, normal loop restarts, export/import, predictor parity, and once-only rewards. Include actual baseline and post-change observations when implemented; the tests are **planned, not executed**.

**Stage boundary:** This is a source planning proposal only. It creates neither an Orcha stage receipt nor permission to implement, merge or deploy.
